# 面试话术提纲（秒杀项目）

> 用法：每个问题先练"一句话开场"，练到不看稿也能说出第一句；后面的顺序记关键词就行。
> 数字全部在你 D9 的压测报告里，**说数字前先看一眼报告**，别凭记忆。

---

## Q0. "介绍一下你最近做的这个秒杀项目"（开场题，必须 60 秒说完）

**一句话开场**：这是个压测驱动的秒杀系统，我把同一套业务做了两版——先做数据库直扣的裸奔版拿到基线，
再用 Redis+Lua+MQ 优化，对比数据都在仓库里。

**按这个顺序**：
1. 业务：1000 件库存，抢购，要求不超卖、不重复下单
2. 第一版（为什么先做烂的）：DB 直扣，压出 ____ QPS，暴露超卖和锁竞争
3. 第二版：Redis 预扣 + Lua 原子 + MQ 削峰 + 唯一索引兜底
4. 结果：____ QPS，P99 ____ ms，库存 0 超卖
5. 现在的瓶颈在 ____

**必须带出**：两个版本的数字对比（这是你和"只会写 CRUD"的人的分界线）

---

## Q1. 为什么用 Redis+Lua，不用数据库行锁？

- 开场：行锁不是错，是**不适合这个场景**——它把并发压到数据库上，而数据库是最难扩的。
- 顺序：① 行锁的代价（锁等待、连接占用、热点行）② Redis 单线程 + Lua 原子性（整个脚本要么全执行）③ 我把"判断库存 + 扣减 + 记录用户"三件事放进一个 Lua，中间不可能被插队
- 必须带出：Lua 里 `if stock >= 1 then decr` 这一段——**判断和扣减不能分开**
- 追问预案：「Lua 脚本会不会阻塞 Redis？」→ 会，所以脚本要短，别在里面做 IO/循环

## Q2. 消息发出去但消费失败怎么办？幂等怎么做的？

- 开场：两层，一层保证消息不丢，一层保证重复消费不出错。
- 顺序：① 发送端：confirm 回调 + 本地重试 ② 消费端：手动 ack，失败进重试队列（重试 N 次后进死信）③ 幂等：`seckill_order` 上 `uk_user_sku` 唯一索引兜底，重复消费直接 DuplicateKey 忽略
- 必须带出：**唯一索引是最后一道防线**，业务代码里的"先查再插"在高并发下必然失效
- 追问预案：「为什么不用 Redis 记已消费 ID？」→ 可以，但要多一次网络往返且会丢；DB 唯一索引是持久化的

## Q3. "排队中"的用户怎么知道结果？

- 开场：秒杀接口只返回"受理成功 + orderNo"，结果靠后续查询。
- 顺序：① 轮询 `/result/{skuId}/{userId}`（简单、够用）② 长轮询/SSE（实时、占连接）③ 推送（成本最高，量级大了才值得）
- 必须带出：我选轮询，因为**前端改造成本最低**，而且秒杀结果 1~2 秒就落地了
- 追问预案：「轮询打爆数据库？」→ 查 Redis 的结果标记，不查 DB

## Q4. 一人一单在高并发下怎么保证？

- 开场：先查后写一定挂——两个请求同时查到"没买过"，就都写进去了。
- 顺序：① Redis Set 预判（快，但可能因为过期/丢数据漏）② DB 唯一索引（慢一点，但绝对可靠）③ 两层的分工：Redis 挡掉 99%，DB 兜最后 1%
- 必须带出：**唯一索引 + 捕获 DuplicateKeyException**，并配合事务回滚库存

## Q5. 限流放网关还是应用层？令牌桶参数怎么定？

- 开场：网关做粗粒度（保护集群），应用层做细粒度（保护热点商品）。
- 顺序：① 网关（Nginx/Spring Cloud Gateway）按 IP/用户限流 ② 应用层用 Redis + Lua 实现令牌桶 ③ 参数：按库存量定——1000 库存不需要放 10 万请求进来，多余的直接拒绝更公平
- 必须带出：**拒绝要快**（早拒绝 = 少一次 DB/Redis 往返），返回 429 并告诉前端"稍后重试"

## Q6. 从 ____ 提到 ____ QPS，瓶颈到底在哪？

- 开场：瓶颈是靠指标定位的，不是猜的。
- 顺序：① 先看应用 CPU（打满 → 加机器/减逻辑）② 再看 DB CPU 和慢查询（打满 → 挪到 Redis）③ 看连接池/线程池排队 ④ 最后看 GC 和 P99 抖动
- 必须带出：我调优前后各看了一次 `vmstat`/容器 stats + DB `SHOW PROCESSLIST`，发现 ____

## Q7. 未支付订单怎么回补库存？

- 开场：两条路，延迟队列（精确）和定时扫表（兜底）。
- 顺序：① RabbitMQ 延迟队列/TTL+死信，15 分钟没支付就回补 ② 兜底：定时任务扫 `status=0 AND create_time < now()-15min` ③ 回补要幂等（先改状态成功才回补）
- 必须带出：**先改订单状态（带条件更新），改成功了才回补库存**，否则并发下会多加库存

## Q8. 如果把 Redis 打挂，系统表现如何？

- 开场：我做了演练，结论是 ____。
- 顺序：① 直接现象（下单全失败 or 降级到 DB）② 我的选择：快速失败 + 返回友好错误，而不是降级到 DB 把 DB 打死 ③ 恢复后要注意缓存重建/库存对账
- 必须带出：**演练的数据**（错误率、恢复时间）——有数据说明你真跑过

## Q9. 这个项目里你做得最不满意的地方？

- 开场：诚实版：压测是同机跑的，数字偏保守，真实分布式环境还得再压一次。
- 顺序：① 已知短板（同机压测、没做分布式限流、没做热点商品分片）② 如果重做会怎么改 ③ 为什么当时没做（时间/收益权衡）
- 必须带出：**能说出取舍逻辑**，比"完美无缺"可信

## 练法（每天 10 分钟）

1. 抽 2 题，**出声**说一遍，手机计时
2. 说不下去的地方做个记号，别背稿——背稿会被追问打回原形
3. 卡壳就回仓库看对应 commit，把"我当时怎么想的"记下来
