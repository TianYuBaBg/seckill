已经帮你写好的（直接用，别改）：

- `SkuStockMapper.deductStock(skuId, qty)`
  ```sql
  update sku_stock set stock = stock - #{qty}, sold = sold + #{qty}, version = version + 1
  where sku_id = #{skuId} and stock >= #{qty}
  ```
  返回 **影响行数**：`1` = 扣成功，`0` = 已经没库存了。**这就是"不超卖"的关键**——不要先 `select` 再判断，那样并发下必超卖。
- 订单表 `seckill_order` 已有 `UK(user_id, sku_id)`，一人一单在数据库层兜底。
- `Result.ok(data)` / `Result.fail(code, msg)`、`BizException(code, msg)`（`GlobalExceptionHandler` 会转成统一 JSON）。

## 三、三个方法怎么写

### 1）detail —— 5 行

1. `skuStockMapper.selectOne(new LambdaQueryWrapper<SkuStock>().eq(SkuStock::getSkuId, skuId))`
2. 查不到 → `throw new BizException(404, "商品不存在")`
3. 查到了 → `return Result.ok(stock.getSkuName() + " 剩余 " + stock.getStock())`

### 2）seckill —— 核心，约 20 行

顺序**必须**是这样（先扣库存、再写订单）：先写订单后扣库存，会出现"订单写了但库存没扣"，超卖。

```java
@Transactional(rollbackFor = Exception.class)   // 别只写 @Transactional，默认不回滚受检异常
public Result<String> seckill(Long skuId, Long userId) {
    // ① 原子扣库存：靠 SQL 的 where stock >= qty 保证不超卖
    int rows = skuStockMapper.deductStock(skuId, 1);
    if (rows == 0) {
        return Result.fail(1001, "已售罄");     // 或 throw new BizException(1001, "已售罄")
    }
    // ② 落订单
    SeckillOrder order = new SeckillOrder();
    order.setOrderNo(生成订单号);                 // 见下方坑 3
    order.setUserId(userId);
    order.setSkuId(skuId);
    order.setQuantity(1);
    order.setStatus(0);                          // 0 = 待支付
    seckillOrderMapper.insert(order);             // 重复下单会撞 UK(user_id,sku_id) → 抛异常 → 事务回滚
    return Result.ok(order.getOrderNo());
}
```

需要你补的只有：

- `seckillOrderMapper` 字段注入（类上已有 `@RequiredArgsConstructor`，加个 `private final SeckillOrderMapper seckillOrderMapper;`）
- `生成订单号`：最简单 `System.currentTimeMillis() + "" + userId`；想好看点用 `UUID.randomUUID().toString().replace("-","")`

### 3）result —— 5 行

```java
SeckillOrder o = seckillOrderMapper.selectOne(
        new LambdaQueryWrapper<SeckillOrder>()
                .eq(SeckillOrder::getUserId, userId)
                .eq(SeckillOrder::getSkuId, skuId));
return o == null ? Result.fail(1002, "没有下单记录") : Result.ok("订单号 " + o.getOrderNo() + "，状态 " + o.getStatus());
```

## 四、四个坑（都会让你卡住，提前说）

1. **`@Transactional` 不生效**：方法必须是 `public`、被 Spring 代理调用（Controller 调 Service 正常；Service 内部 `this.xxx()` 自调用不生效）。
2. **业务码不是 0 时接口返回 200**：我们所有"失败"都走 `Result.fail(code, msg)`，HTTP 仍是 200，靠 `code` 区分。`verify.py` 就是这么判断的。
3. **订单号重复**：`uk_order_no` 会报 `Duplicate entry`。用时间戳+userId 或 UUID。
4. **重复秒杀同一件商品**：会撞 `UK(user_id, sku_id)` 抛异常 → 事务回滚 → 库存回补。现在已经被全局异常处理成友好返回 **`{"code":1003,"msg":"你已经抢到过了，一人一单"}`**（我实测过），D5 再加 Redis 预检。

> 附：结果查询的真实路径是 **`GET /api/seckill/result/{skuId}/{userId}`**（是路径参数，不是 `?userId=`）。
> 自己 curl 时别再写错，写错了会直接看到 404/405 的友好提示而不是 500。

## 六、面试可以讲的 3 句话（今天就用得上）

1. "这一版是**最笨但最正确**的版本：靠 `update ... where stock >= 1` 的条件更新保证原子性，影响行数为 0 就说明卖完了。"
2. "我先扣库存再写订单，整个方法在一个事务里；如果订单插入失败（比如撞了一人一单的唯一索引），库存会自动回滚，不会出现少卖。"
3. "它的瓶颈很明显：一次秒杀要 2 次 DB 写 + 1 次事务提交，QPS 上不去。D3 我会用 200 并发压一遍拿到基线数字，D9 再用 Redis 预扣 + 异步下单把它拉上去，前后对比就是性能优化的完整闭环。"
